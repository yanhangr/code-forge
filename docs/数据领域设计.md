你这里的理解比我上一版更进一步，而且我认为应该据此把架构再修一次。**你们实际上需要两层不同目的的隔离，同时 Session 不是简单“目录父子关系”，而应该成为把用户文件、配置、Agent 状态和一次次 Run 串起来的逻辑主线。**

最关键的结论先说：

> **第一层是 User 隔离：防止 U001 的 Agent 看到或修改 U002 的任何资源。**
>
> **第二层是 Execution 隔离：防止 U001 自己的 Agent 生成的 Python/Bash 等不可信代码破坏 U001 的系统数据、Runtime 容器乃至宿主机。**

因此我现在不建议简单地说：

```text
只把 /users/U001/workspace 挂进 Sandbox
```

更合适的是一个**双层 Sandbox / Container 模型**。

---

# 一、两层隔离分别解决什么问题

最终应该是：

```text
                       Host / K8s Node
                              │
                     cf-agent Platform
                              │
                    ┌─────────┴─────────┐
                    │                   │
                 User U001           User U002
                    │                   │
          ┌─────────▼─────────┐ ┌──────▼──────────┐
          │ User Environment  │ │ User Environment│
          │     U001          │ │      U002       │
          │                   │ │                 │
          │ 只能访问U001数据   │ │ 只能访问U002数据 │
          └─────────┬─────────┘ └─────────────────┘
                    │
                    │
              Run / Tool Call
                    │
          ┌─────────▼─────────┐
          │ Execution Sandbox │
          │                   │
          │ Python / Bash     │
          │ Git / Files       │
          │                   │
          │ CPU/内存/网络限制 │
          │ 文件系统限制       │
          └───────────────────┘
```

这两层不能合并理解。

---

# 二、第一层：User Isolation

第一层解决的是：

> **U001 永远不应该访问 U002。**

例如 NAS：

```text
/cf-agent/
└── tenants/
    └── T001/
        └── users/
            ├── U001/
            ├── U002/
            └── U003/
```

U001 的 User Environment 只能获得：

```text
/users/U001/
```

绝对不能看到：

```text
/users/U002/
/users/U003/
```

所以未来“一用户一个 Docker”其实非常合理：

```text
U001
 ↓
Docker-U001
 ↓
只挂载 /users/U001


U002
 ↓
Docker-U002
 ↓
只挂载 /users/U002
```

即使 U001 的 Agent 执行：

```bash
ls /users
```

或者：

```bash
cd ../U002
```

也不应该存在任何访问可能。

这属于：

> **用户级文件系统安全边界。**

---

# 三、第二层：Execution Sandbox

但即使 U001 已经被隔离了，仍然不应该允许 Agent 生成的代码直接在：

```text
Docker-U001
```

里无限制执行。

例如模型生成：

```bash
rm -rf /
```

或者：

```python
os.system("...")
```

或者：

```bash
kill -9 ...
```

或者扫描内网、修改 Runtime 自身文件。

所以真正执行：

```text
Python
Bash
Git
```

应该再进入一层：

```text
Execution Sandbox
```

例如：

```text
User Environment U001
        │
        └── Run R001
               │
               ▼
        Execution Sandbox
```

这里负责：

```text
CPU Limit
Memory Limit
Process Limit
Filesystem Isolation
Network Policy
Syscall Limit
Timeout
Readonly Mount
```

所以两层安全职责完全不同：

| 隔离层               | 防什么                                   |
| ----------------- | ------------------------------------- |
| User Isolation    | 防 U001 访问 U002                        |
| Execution Sandbox | 防 Agent 代码破坏 U001 Runtime / Host / 网络 |

这个设计我认为应该正式写进架构。

---

# 四、那到底挂 `/users/U001`，还是只挂 `/users/U001/workspace`？

答案是：

> **两层挂载方式不同。**

这是我们前面理解差异的关键。

## 外层 User Environment

可以挂：

```text
/users/U001/
```

因为这个环境本身已经是：

> U001 专属的受信 Agent Runtime 环境。

里面可以看到：

```text
/users/U001/
├── workspace/
├── sessions/
├── config/
├── tool-output/
└── snapshots/
```

这样非常适合未来：

```text
一个用户
=
一个Docker
```

整个用户迁移也很容易。

---

## 内层 Execution Sandbox

绝对不要把：

```text
/users/U001/
```

整个挂进去。

执行 Python/Bash 的 Sandbox 只获得：

```text
/workspace
/skills
/runtime
```

例如：

```text
Execution Sandbox

/workspace
    ↓
/users/U001/workspace

/skills
    ↓
本次Run需要的Skill Bundle，只读

/runtime
    ↓
临时执行目录
```

这样即使 Python 代码失控，它也看不到：

```text
sessions/
config/
snapshots/
```

这才是正确的安全模型。

不用一定画在总体架构图上。

它负责：

```text
Session
+
User
+
Project
+
Agent Config
+
Skill Config
+
Permission
+
Runtime
       ↓
Effective Run Context
```

# 三十四、整个启动流程最终应该是

用户：

```text
Session S001
发送消息
```

服务端：

```text
1. 查 Session S001

2. 得到：
   tenant_id = T001
   user_id    = U001
   project_id = P001
   agent_id   = A001

3. 找到 User Root：
   /users/U001

4. 找 Workspace：
   /users/U001/workspace

5. 找 Project：
   /workspace/projects/P001

6. Resolve Agent A001

7. Resolve 当前有效 Skills

8. 固化 RunConfigSnapshot

9. 创建 Run R001

10. 创建/取得 U001 User Environment

11. 创建 Execution Sandbox

12. 挂载：
    Project/Workspace RW
    Skill Bundle RO
    Runtime Temp RW

13. 恢复 LangGraph Thread

14. 加载必要 Transcript

15. 开始执行
```

# 三十五、最终我建议你们把这几个概念彻底钉死

**User Root**

```text
/users/U001
```

用于：

> 物理数据隔离、迁移、备份。

---

**Workspace**

```text
/users/U001/workspace
```

用于：

> 用户长期工作文件。

---

**Session**

用于：

> 长期对话和资源关联。

它“串”：

```text
User
Workspace
Project
Agent
Thread
Transcript
Run
```

---

**Run**

用于：

> 固化一次真实执行环境。

它“串”：

```text
Agent Version
Skill Versions
Tools
Sandbox
Snapshot
Tool Output
Execution Records
```

---

**User Environment**

用于：

> 防 U001 越权访问 U002。

---

**Execution Sandbox**

用于：

> 防模型生成代码破坏 User Runtime / Host。

---

**Skill Bundle**

用于：

> 把本次 Run 实际需要的 Skill 动态加载进 Runtime，而不是硬编码在 Workspace。

---

我认为这样调整后，之前那个“`/users/U001` 下面有很多目录，到底谁把它们串起来”的问题就清楚了：

> **物理上由 User Root 聚合。**
>
> **逻辑上由 Session 串长期上下文。**
>
> **执行时由 RunContext 串具体资源版本。**
>
> **Runtime Context Resolver 负责把这些逻辑关系解析成真正的挂载、Skill Bundle 和 Sandbox 配置。**

这个模型也正好适合你未来的 **一 User 一 Docker + 每次代码执行再套一层 Sandbox** 的两级隔离方案。
